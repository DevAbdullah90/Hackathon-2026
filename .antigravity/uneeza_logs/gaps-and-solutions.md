## Gap 1 — Missing Actions Endpoint

### What is Missing
The `actions` table exists in the database and is populated by the **Planning Agent**
at Step 5 of the pipeline. It contains real tactical decisions like:
- `DISPATCH_RESCUE_TEAM`
- `REROUTE_TRAFFIC`
- `ALERT_CITIZENS`
- `DISPATCH_DRAINAGE_CREW`

However, **there is no API endpoint to retrieve these actions per incident.**
The `simulation.py` reads actions internally, but the dashboard has no way to
display what the Planning Agent decided to do.

### Impact
- Judges cannot see the "Response Plan" generated by the AI
- The simulation state endpoint exists (`GET /simulation/state/{id}`) but only
  shows action statuses — not the full action details from the perspective of
  the incident dashboard
- The web dashboard's "Tactical Actions" panel would have no data source

### Required Change

```
NEW ENDPOINT:
GET /api/v1/incidents/{incident_id}/actions

Response example:
[
  {
    "id": "uuid",
    "type": "DISPATCH_RESCUE_TEAM",
    "status": "PENDING",
    "predicted_side_effects": "Minor traffic congestion on Route 7",
    "action_metadata": { "units": 3, "eta_minutes": 12 },
    "updated_at": "2026-05-18T10:22:00Z"
  },
  ...
]
```

### File to Modify
`backend/app/api/api_v1/endpoints/incidents.py` — add a new route at the bottom.

## Gap 2 — Missing Resources Endpoint

### What is Missing
The `resources` table is populated by the **Resource Allocation Agent** (Step 4).
It tracks the current pool of emergency resources:
- `ambulance`
- `rescue_team`
- `drainage_crew`
- `police_unit`

Each row has `total_count` and `available_count` fields. Allocated units =
`total_count - available_count`. The dashboard counters API (`/dashboard/stats`)
already sums these up, but there is **no endpoint to show the full resource pool**
with a breakdown per type, per incident.

### Impact
- Cannot display a "Resource Allocation Board" on the dashboard
- Judges cannot see which crews were dispatched to which incident
- The `/dashboard/stats` only gives aggregate numbers — no breakdown

### Required Change

```
NEW ENDPOINT:
GET /api/v1/resources

Response example:
[
  {
    "id": "uuid",
    "type": "ambulance",
    "total_count": 20,
    "available_count": 6,
    "allocated_count": 14,
    "assigned_to_incident": "incident-uuid",
    "location": "Islamabad Base Station"
  },
  ...
]
```

### File to Modify
Create `backend/app/api/api_v1/endpoints/resources.py` and register in `api.py`.

## Gap 3 — Frontend Blank Screen (Pipeline Delay)

### What is Happening

This is the **most visible issue** during the hackathon demo. When a signal is
submitted, the map shows nothing for 40–90 seconds. Here is exactly why:

### Root Cause — Step by Step

```
USER SUBMITS SIGNAL
       ↓
POST /api/v1/signals/ → returns HTTP 201 IMMEDIATELY
       ↓
Background task starts (pipeline runs asynchronously)
       ↓
┌──────────────────────────────────────────────┐
│  Step 1: Signal Agent    → LLM call ~5–10s   │
│  Step 2: Detection Agent → LLM call ~8–15s   │
│  Step 2.5: Verification Agent (conditional)  │
│  Step 3: Severity Agent  → LLM call ~5–10s   │
└──────────────────────────────────────────────┘
       ↓
  ONLY NOW is the Incident written to the database
       ↓
┌──────────────────────────────────────────────┐
│  Step 4: Resource Agent  → LLM call ~5–10s   │
│  Step 5: Planning Agent  → LLM call ~8–12s   │
│  Step 6: Notification Agent → LLM call ~3–5s │
└──────────────────────────────────────────────┘
       ↓
Total pipeline time: ~40–90 seconds

Meanwhile, frontend map.tsx polls every 10 seconds:
GET /api/v1/incidents/active → returns [] (empty list)
       ↓
Map shows nothing until the incident is in DB
```

### Why Can't We Just Show It Sooner?

The `Incident` row is only created **after the Detection Agent confirms** that
the signal is a real flood and **after the Severity Agent scores it.** The backend
intentionally waits for both before writing to the DB because unconfirmed signals
should not appear as active incidents on the map.

### Solution Options

**Option A (Recommended for Hackathon) — Signal Status Polling Endpoint**

Add a lightweight endpoint that the frontend can poll after submission to show
a real-time progress indicator (loading bar / progress steps):

```
NEW ENDPOINT:
GET /api/v1/signals/{signal_id}/status

Response example:
{
  "signal_id": "uuid",
  "pipeline_stage": "severity_agent",
  "stage_index": 3,
  "total_stages": 6,
  "incident_id": null,       ← null until confirmed
  "status": "PROCESSING"     ← "PROCESSING" | "CONFIRMED" | "REJECTED"
}
```

The frontend can poll this every 2 seconds after submission and display:
```
Signal Received ✅ → Signal Agent ✅ → Detection ✅ → Severity 🔄 → ...
```

**Implementation:** Requires a lightweight `pipeline_status` tracking dictionary
in memory (or a `SignalStatus` table) that the pipeline updates at each step.

**Option B (Simpler) — "Monitoring" Incident on Detection Confirm**

Create a preliminary `Incident` with `status = "monitoring"` immediately after
the Detection Agent confirms, without waiting for Severity. Update it to
`"confirmed"` after Severity completes. This makes the incident appear on the
map ~15–25 seconds sooner.

## Gap 4 — WebSocket Early Log Loss (Pre-Incident Phase)

### What is Happening

This is a **separate but related issue** to Gap 3. Even if the map had an incident
to show, the `LiveLogStream` component would still miss the first 3 agents' logs.

### Root Cause — Detailed

```
Pipeline starts for signal_id = "abc-123"

[Signal Agent logs]     → emit_log() called
                          → broadcasts to WS channel: "triage"
[Detection Agent logs]  → emit_log() called
                          → broadcasts to WS channel: "triage"
[Severity Agent logs]   → emit_log() called
                          → broadcasts to WS channel: "triage"

↓ Incident created with id = "xyz-789"

[Resource Agent logs]   → emit_log() called
                          → broadcasts to WS channel: "xyz-789" ✅
[Planning Agent logs]   → broadcasts to WS channel: "xyz-789" ✅
[Notification Agent logs] → broadcasts to WS channel: "xyz-789" ✅

Meanwhile, FRONTEND:
LiveLogStream component receives incidentId = "xyz-789"
Connects to: ws://.../api/v1/ws/xyz-789

→ Receives: Resource, Planning, Notification logs ✅
→ MISSES:   Signal, Detection, Severity logs ❌ (were on "triage" channel)
```

### Why Does This Happen?

The `emit_log` tool in `tracer.py` uses this logic:
```python
target_id = incident_id if incident_id else "triage"
await manager.broadcast(target_id, payload)
```

So logs before an incident is confirmed always go to the `"triage"` channel.
The frontend `LiveLogStream` never subscribes to `"triage"` because it only
knows about `incidentId` (which doesn't exist yet at that point).

### Solution

**Frontend change in `map.tsx` + `LiveLogStream.tsx`:**

1. After `POST /signals` returns, extract the `signal_id` from the response.
2. Navigate to a "Processing" screen immediately with the `signal_id`.
3. `LiveLogStream` connects to: `ws://.../api/v1/ws/triage` initially.
4. When the incident is confirmed (polled via Gap 3's status endpoint),
   switch the WebSocket to `ws://.../api/v1/ws/{incident_id}`.

```
POST /signals → { signal_id: "abc-123" }
       ↓
Navigate to ProcessingScreen(signal_id="abc-123")
       ↓
Connect WS → ws://.../api/v1/ws/triage
       ↓
LiveLogStream shows: Signal Agent ✅, Detection ✅, Severity ✅ (LIVE!)
       ↓
Status polling confirms incident_id = "xyz-789"
       ↓
Switch WS → ws://.../api/v1/ws/xyz-789
       ↓
LiveLogStream shows: Resource ✅, Planning ✅, Notification ✅
```

**Backend change (optional improvement):**

Instead of a single `"triage"` channel, broadcast pre-incident logs to
`"triage_{signal_id}"` so multiple simultaneous pipeline runs don't mix logs:

```python
# tracer.py
target_id = incident_id if incident_id else f"triage_{signal_id}"
```
